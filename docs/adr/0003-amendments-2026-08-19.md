## Amendment A (G2) — cross-pod reply path: NO engine change (charter-only)

### Status

Head office (#827) adopted option (iii) — every pane a single-member pod — for
evaluation first. QA's architecture review then verified the no-engine-change
chain against the engine and confirmed it fail-closed at every hop; head
office (#847) accepted: Amendment A is ratifiable as a charter-only change,
subject to MF-5. The (iii) evaluation evidence (20 panes / 35 pairs in the
last 500 POC messages; 97% manager↔manager) remains on file as the fallback
position if live usage disproves the chain.

**Fallback blocking conditions (from the v2 review, head-office #854):** the
(iii) fallback is NOT QA-cleared. Two v2 must-fixes must be resolved in the
text before (iii) is ever adopted:
- **v2-MF-1 (single-member pod lifecycle):** closed pods count toward the
  64-pod ceiling forever and names are never reusable — under (iii) + charter
  §6.2 churn the ceiling is a monotonic countdown (~45 retirements from
  exhaustion). Adoption requires a stated lifecycle policy for pane retirement
  and ceiling math re-derived from it.
- **v2-MF-2 (dead single-member pods keep LIVE leader tokens):** token
  deletion fires only inside promotion; a successorless pod's dead leader
  token stays valid forever — every pane death would leave a working
  credential. Adoption requires a death-verified token-retirement path (watch
  sweep deletes the token hash of a verified-dead leader with no viable
  successor, or mandatory pod close on pane retirement — which feeds
  v2-MF-1's countdown).
- Also recorded from v2: unilateral channel open is sufficient at current
  scale only conditionally (a consent/accept step is the named fix if the
  fallback triggers fire); standing channels degrade the awareness feed to
  "who talks to whom, how much" (AR-2); close→re-open churn can evict feed
  history (v2-AR-1).

### The chain (verified legal under D4 as ratified, every hop token-authenticated)

1. member B (pod X) → leader X: rule 1 (intra-pod).
2. leader X → leader Y on an open channel: rule 2.
3. reply leader Y → leader X on the same channel: rule 2 (channels are
   bidirectional).
4. leader X → member B: rule 1 (intra-pod fan-down; "the roster is never an
   address; intra-pod fan-out is the members' own business").

QA verification highlights: no path delivers cross-pod mail to a worker
(pods.ts:366-367); a forged reply cannot ride a channel down to a foreign
worker (the parent message cannot exist — workers never send cross-pod);
reply recipient is engine-derived from the parent, not sender-named.

### The charter amendment (head office owns; engine untouched)

- §2.5 changes from "the watcher does the last hop; never relay replies
  manually" to "the forwarding manager relays replies down to its own member;
  intra-pod fan-down is manager duty." The watcher's auto-last-hop retires
  with the POC lane.
- D4 stays exactly as ratified. No cross-pod worker addressability, ever.
- **MF-5 (stranded-reply recovery, REQUIRED text):** promotion deletes the
  dead leader's token hash, and inbox auth is per-name — mail addressed to a
  dead leader is permanently unreadable, including by the promoted successor.
  If a peer leader dies mid-relay, the reply strands and the requester would
  wait forever. Uniform recovery: the forwarding manager times out a relayed
  request after 120 s without a reply (mirroring the POC escalation
  interval), runs `pod show` on the peer pod, and re-issues the request by
  name to the CURRENT leader over the same channel. The dead leader's inbox
  is abandoned; no recovery is attempted against it. One retry, then escalate
  to head office. No manager invents their own retry semantics.
- **AR-1 disclosure:** "replies inherit the parent channel" is convention,
  not mechanism — CoordinationMessage carries no channel field; containment
  holds because at most one open channel exists per pod pair. This invariant
  is load-bearing; if it ever relaxes, reply binding must become real.
- **AR-2 disclosure:** hop-4 fan-down rides the manager's own authority;
  correlation state (--on-behalf-of) and relay honesty are manager duties,
  not engine guarantees — same trust shape as the POC watcher last hop.
- **AR-6 disclosure (runbook lines):** double-reply to one parent is a
  permitted no-op replay; `compact` can delete a parent before its reply
  arrives (reply then fails with "unknown message" — re-issue per MF-5).

## Amendment B (G3) — roster mutation via `pod appoint` (as ruled)

### The ruling

Head office (#827): SHIP `pod appoint`. Roster growth is orchestrator-mediated
appoint. Close/recreate is rejected (pod names never reusable, D2.3 churn
unacceptable).

### Scope under ruling + (iii) evaluation

1. **Ship `interlock pod appoint --pod <pod> --leader <member>
   --orchestrator-token <token>`** as specified at ADR-0003 D2 line 131:
   appointee must be a current roster member; prior leader demotes atomically;
   never two leaders; awareness event emitted. (Closing an implementation gap
   on ratified behavior — it is also on the v0.0.4 feature-completeness audit
   list.)
2. **Roster growth:** to make appoint able to grow a roster (not just re-point
   leadership among existing members), extend the appoint surface:
   `pod appoint --pod <pod> --member <name> --orchestrator-token <token>
   [--role leader|worker] [--no-succession]` — adding a new name appoints it
   INTO the roster (orchestrator-gated, mint-once token, exclusivity +
   different-hash squat guard, MAX_ROSTER_SIZE enforced, appended to
   succession unless --no-succession, awareness event). Re-pointing leadership
   among existing members stays the base case. One command, two modes,
   consistent with "the orchestrator owns topology" (D2).
3. **No removal command.** Append-only growth; death-verified succession and
   pod close remain the only exits. "Only provable death mutates the roster"
   stays true for removal; growth mirrors creation authority.
4. **MF-1 (REQUIRED text):** the duplicate check spans ALL pods INCLUDING
   CLOSED ones — PodMember records persist forever at pod close and the
   load-time invariant rejects duplicate member names across all pods. A name
   from a closed pod is never reusable, same rule as pod names.
   Implementation copies createPod's guard wholesale (it does not filter on
   pod status).
5. **MF-2 (REQUIRED text):** appoint/add-member rejects the reserved name
   `orchestrator`, exactly as createPod and registerMemberToken do — writing
   memberTokens directly without this check would let the operator overwrite
   the orchestrator's token hash: instant loss of topology control.
6. **MF-3 (REQUIRED text — decision: option b):** appoint/add-member does NOT
   revive auto-promotion. Death evaluation for a leaderless pod is terminal
   once evaluated (diedAt set, permanent early-return); a member added into a
   leaderless wedge pod is never promoted automatically. `pod appoint` is the
   ONLY recovery from a leaderless wedge. Said explicitly so every operator
   knows: staffing into a wedged pod does not heal it — appoint does.
7. **MF-4 (REQUIRED text):** `pod appoint` rejects any appointee with doneAt
   set. doneAt is terminal; a done appointee becomes a leader who fails every
   leader-authority check while alive, so no auto-promotion can ever fire — a
   wedged pod with a breathing corpse for a leader. "Appointee must be a
   current roster member AND must not have doneAt set."
8. **AR-3 disclosure:** dead workers keep live tokens until pod close; only
   leader death is evaluated. With staff-on-demand churn and no removal, the
   dead-but-tokened set and roster-cap (16) pressure grow — pods eventually
   close/recreate (the designed answer) and rotated staff churn member names.
   Death-verified worker token deletion is recorded as future work.
9. **AR-4 disclosure:** the squat race window (unauthenticated first-come
   session register between staffing decision and appoint) is identical to
   create's and already disclosed in ADR-0003; the command aborts loudly.
10. **AR-5 disclosure:** `--no-succession` members can never be auto-promoted;
    leadership reaches them only via `pod appoint`. Staffing playbooks must
    not assume otherwise.

### Explicitly rejected (per ruling)

- Close/recreate for roster change (name churn, D2.3).
- v1's separate `pod add-member` command — folded into `pod appoint` per the
  ruling's "growth via orchestrator-mediated appoint" framing.
