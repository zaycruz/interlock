# Interlock go-to-market V1

## Outcome

An agent discovers useful work, claims its exact scope, coordinates with other agents, survives interruption, and delivers an accepted result without a human transferring context between agents.

The initial market is developers who run multiple local coding agents in Git worktrees. Interlock is a local same-user coordination product. Hosted coordination, a new tracker, a graphical application, model orchestration, and new runtime dependencies are outside V1.

## Principles and decision

- Reuse the existing Beads and SQLite lifecycle.
- Keep one issue authority and explicit execution ownership.
- Keep policy and safety checks in deterministic code.
- Give CLI and MCP the same supported worker capabilities.
- Measure workflow outcomes through real public interfaces.

Drivers: coherent ownership, safe recovery, low operating cost.

Option A extends coordination with explicit Beads/work-contract linkage. It preserves existing noncoding tasks and messaging, but requires recoverable cross-store operations. Option B moves all task operations into Beads. It reduces task duplication but expands tracker integration and makes noncoding coordination depend on Beads. Choose A. Beads remains authoritative for linked issue title, value, and acceptance. Coordination owns execution context, references, communication, and evidence. No generic tracker interface is required.

The canonical coding-task reference contains Git-common repository identity plus Beads ID. The chosen worktree is separate. Task IDs remain the communication reference. Independent noncoding tasks remain supported and do not grant file ownership.

## Required behavior

1. Linked coding-task claim obtains the existing exact-path lease contract. Duplicate task or path claims fail. Persist the execution reservation before a remote mutation. Resolve ambiguous outcomes against the exact contract.
2. Expose worker discovery, inspect, create, update, withdraw, claim, checkpoint/progress/block, release, complete, recover, and resume through CLI and MCP. Keep deployment administration outside worker authority.
3. Link messages and results to tasks. Task context includes authorized discussions, acceptance, paths, owner, blockers, checkpoint, and result references. Preserve useful context during compaction.
4. Require acceptance evidence for completion. Identify declared evidence versus checks actually executed. Prevent generic stage changes from bypassing linked completion. Staged changes must remain inside the lease scope.
5. Recover verified-dead claims and preserve resume context. Do not reclaim quiet, alive, unknown, or ambiguous sessions. Snapshot execution identity at claim time.
6. Deduplicate retried messages by sender and request ID. Reject key reuse with a different payload. Preserve retry semantics across compaction.
7. Allow revision-checked task correction and withdrawal with owner/creator authorization. Preserve terminal history.
8. Make summary reads bounded and expose structured MCP results and discoverable task context. Preserve quiet delivery at natural seams.
9. Adopt the engineering profile, size and complexity enforcement, root and adapter CI, relevant static/dependency checks, and independent adversarial review. Do not hide legacy debt or add runtime dependencies.
10. Align GOAL, README, capability map, host setup, product positioning, recovery instructions, and release notes with proven behavior. Implement and verify the Pi lifecycle requirement using the supported host boundary.

## Delivery sequence

A. Baseline tests and quality adoption. Capture present failures. Write behavior-preserving cleanup plan before extraction.
B. Extract existing lease application behavior from CLI. Extract coordination task/argument helpers along cohesive boundaries. Preserve public behavior with current regression tests.
C. Add canonical linked execution, durable reservation/recovery, evidence, revision edits and resume context.
D. Add task-linked retry-safe communication and bounded discovery.
E. Expose the complete worker workflow through MCP. Verify parity through actual clients.
F. Verify adapters and packed installation. Run three disposable repository smokes, real two-worktree contention, crash/retry dogfood, and safe Atlas smoke if clean.
G. Run full quality gate, independent correctness/security review, fix findings, and inspect the release artifact. Write exact release evidence and remaining operational limits. Do not call V1 complete before all gates pass.

## Cleanup plan

Lock current behavior with the existing CLI/core/coordination/MCP suites. Extract lease application operations out of CLI to remove the dependency-cycle risk. Extract task handling out of the oversized coordination command module. Keep parsing shared and small. Reduce oversized state validation by cohesive entity validators. Do not introduce a service framework, event bus, generic repository interface, or speculative compatibility layer.

## Premortem

- Beads succeeds and local state persistence fails: preserve an intent before the remote call; reconcile the exact contract; test a crash in each window.
- An agent crashes or its PID is reused: retain immutable claim identity; verify death; preserve checkpoint and ownership safety in tests.
- A retry repeats a side effect or compaction deletes the receipt: persist stable request identity and result; test after compaction and process restart.

## Verification and release evidence

The companion test specification is the completion checklist. Unit tests prove transitions and authorization. Public module/CLI tests prove persistence and failure outcomes. MCP tests use a real client and transport. Dogfood uses built/packed artifacts and disposable state. Record each command, exit status, repository/contract IDs, observed results, and unverified limits. Measure completion without human coordination, interventions, blocker age, recovery time, duplicate effects, and evidence completeness.

Independent architecture and critic reviews approved the plan before implementation. The user authorized delivery. Implementation uses bounded specialist assignments and independent verification.

## Lifecycle convergence and acceptance contract

Canonical repository/Beads linkage is unique across task IDs. An existing active Beads contract is discoverable by its actual stored contract ID; never infer a task link from a matching title or pane.

The shared application boundary applies linked-work rules to every entry point, including legacy claim/complete/release/resolve/reconcile. Coordination is an execution index. Inspection displays observed lease state and pending operations without changing them. Claim reserves linked execution before external effects. Complete persists evidence and completion intent before Beads close. Release and dead-worker recovery retain a recoverable intent until Beads and lease outcomes converge. An ambiguous or mismatched remote outcome retains the intent and refuses a new claim. Implement these as explicit operations, not a generic distributed transaction framework.

A linked completion record binds to the exact contract ID and the acceptance text captured at claim. It contains a result summary, artifact references, and observed verification results for the required acceptance items. Agent-supplied descriptions remain labelled as declarations. Required verification commands run in the claimed worktree and record command, exit status and output evidence. Missing evidence, failed verification, changed acceptance, mismatched contract identity, or out-of-scope staged changes block completion. Do not equate an arbitrary evidence string with verified acceptance. Keep the check specification explicit and small; do not implement scheduling or a CI service.

Upgrade proof starts with version-2 state containing unlinked tasks, queued messages, a live lease, and a pending completion. Existing unlinked tasks remain usable as coordination-only work. Preserve ownership and terminal history on upgrade and restart. Introduce an explicit version refusal for a downgrade that cannot preserve the new lifecycle invariants; document this limit before packaging.

The combined dogfood must use two independent clients and packed public interfaces. It must finish with zero human context transfers, zero duplicate effects, one valid owner per task/path, and observed evidence for every required acceptance item. Capture recovery duration as a measurement; no invented latency threshold. Repeat the scenario across an agent restart and a lost-response retry.

Architecture review approved this revision with two constraints: inspection/status stays a read-only projection and only explicit lifecycle/reconcile commands mutate ownership; capture verification command specifications with the acceptance snapshot at claim, then execute those captured commands with bounded timeouts. Completion callers cannot replace them with easier commands.
